# 中国象棋证明路线：明确数学命题

这份文档把“Pikafish 分数支持某个预期”拆成可证明的数学命题。核心立场：

- 引擎评分不是证明。
- 数学证明必须落在有限状态、递推定义、证明证书和独立校验器上。
- Pikafish、PCN、DF-PN 只负责减少需要展开的节点，不能替代闭合证明。

## 1. 先把规则变成有限游戏

当前最有价值的规则假设是：

```text
第三次重复，造成者负。
```

把基础局面定义为：

```text
B = 棋盘 + 当前行棋方
```

把证明用扩展状态定义为：

```text
E = (B, history_count)
history_count: 每个基础局面出现 0 / 1 / 2 次
```

如果某一步会让目标基础局面第 3 次出现，则这一步对走子方是立即失败。否则这一步合法进入新扩展状态，并把目标基础局面的计数加一。

### 定理 A：这个规则下游戏有限

设基础局面总数为 `N`。在任何非失败走法后，所有历史计数之和都会增加 1，并且每个基础局面最多计到 2。

因此非失败路径长度最多为：

```text
2N - 1
```

这说明：即使没有长将、长捉、自然限着，加入“第三次重复造成者负”后，扩展游戏仍然没有无限合法非失败对局。

这一步非常关键。它把中国象棋证明问题从“可能无限循环”变回“有限双人零和完全信息游戏”。

## 2. 胜负递推定义

对扩展状态 `E` 定义 `V(E)`：

```text
WIN  = 当前行棋方存在一步，使对手进入 LOSS，或直接将死对方。
LOSS = 当前行棋方所有可走选择都导致自己立即失败，或进入对手 WIN。
```

在当前规则下，如果不额外定义和棋终局，理论上每个扩展状态都应归入 `WIN / LOSS` 之一。

更严格地写：

```text
V(E) = WIN
  iff exists move m:
      m 不造成己方第三次重复失败
      and V(apply(E, m)) = LOSS

V(E) = LOSS
  iff for all legal moves m:
      m 造成己方第三次重复失败
      or V(apply(E, m)) = WIN
```

因为定理 A 已经保证扩展游戏有限，所以这个递推可以用反向归纳定义，不依赖引擎。

## 3. 我们真正要证明的命题

如果预期是“红方先行必胜”，数学命题是：

```text
V(start_position_with_empty_history) = WIN
```

如果先做弱目标，可以改成：

```text
存在某个红方首着 r，使 V(after(r)) = LOSS for Black
```

也就是：

```text
红方有一个首着，把黑方送入必败扩展状态。
```

如果要证明某个评分阈值有效，命题不能写成“Pikafish 大于 T 就必胜”。它必须写成有限域命题：

```text
对样本集合 S 内所有状态 E：
如果 Pikafish_score(E) >= T，
则 verifier 能校验一个 V(E)=WIN 的证书。
```

这个结论只对 `S`、固定规则、固定证书格式成立，不能自动外推到全部中国象棋局面。

## 4. 证明证书格式

最小证书可以是 AND/OR 证明树，也可以压缩成 DAG。

### WIN 证书

一个 `WIN` 节点只需要给出：

```text
当前状态 E
一个走法 m
子证书证明 apply(E, m) 是 LOSS
```

校验器检查：

- `m` 是合法走法。
- `m` 不造成当前方第三次重复失败。
- 子证书确实证明子状态为 `LOSS`。

### LOSS 证书

一个 `LOSS` 节点必须覆盖当前方全部选择：

```text
当前状态 E
所有合法走法 m1, m2, ..., mk
每个 mi 要么立即造成第三次重复失败
要么有子证书证明 apply(E, mi) 是 WIN
```

校验器检查：

- 列出的走法集合等于规则生成器产生的全部合法走法。
- 每条边都有立即失败理由或闭合子证书。

这就是数学上最清楚的证明对象。它不要求人类读完整树，只要求校验器能逐点检查局部正确性。

## 5. 压缩证明树的合法方式

### 5.1 转置 DAG

如果两个路径到达同一个：

```text
棋盘 + 当前行棋方 + 历史计数签名
```

可以共用一个子证书。

注意不能只按棋盘共用。重复规则依赖历史，直接按棋盘复用会产生 GHI 错误。

### 5.2 Merkle 证书

大型证明不需要一次性放进内存。每个节点可以写成：

```text
node_hash = H(state, value, move_list, child_hashes)
```

校验时按需流式读取。最终只公开根哈希、证书文件和验证程序，也可以复现检查。

这解决的是“证书太大怎么放”的问题，不解决“证书怎么找到”的问题。

### 5.3 残局库边界

当搜索进入低子力局面时，不继续展开，而是查经过独立逆向分析得到的 WDL/DTM 表。

证书中写：

```text
leaf = tablebase_hit
tablebase_id
position_index
value
```

校验器只需要验证表库哈希和索引值。

### 5.4 对称和规范化

中国象棋至少有左右镜像对称。可以把局面规范化为左右镜像中字典序较小的一边，减少重复证明。

但规范化必须同时作用于：

- 棋盘。
- 走法。
- 历史计数签名。
- 证书哈希。

否则仍会破坏重复规则下的正确性。

## 6. 搜索如何减少证明量

### 6.1 DF-PN / PNS

Proof-number search 的作用是优先展开“最可能被证明”的节点。

它不改变证明定义，只改变展开顺序：

```text
pn = 证明当前节点为 WIN 还需要的估计代价
dn = 证明当前节点为 LOSS 还需要的估计代价
```

这适合我们的目标，因为开局证明不是平均展开，而是希望找到很窄的一条胜利主线，同时对对手所有反驳做闭合。

### 6.2 Pikafish 分数

Pikafish 可以提供：

- 候选走法排序。
- 静态局面分数。
- MultiPV 反驳集合。
- proof-cost 初始估计。

但它不能提供：

- 必胜证明。
- 可删分支的数学理由。
- 阈值必胜定理。

所以正确用法是：

```text
Pikafish 负责先搜哪里。
Verifier 负责判断是否已经证明。
```

### 6.3 Proof Cost Network

如果以后训练网络，不训练“胜率”，而训练：

```text
从这个局面闭合证明需要多少节点
```

这比胜率更贴近证明任务。强棋力模型不等于强证明器；证明器需要的是更快找到闭合证书。

## 7. 对当前实验结果的解释

现在已有的 depth 30 开局探测显示：

```text
44 个红方首着中，最高红方视角只有 +22 cp。
```

这不支持“开局第一步已经有明显引擎胜势”的经验判断。

但它也不反驳“红方必胜”。原因是：

- 深度 30 不是完全搜索。
- `+22 cp` 可能只是短期均势评估。
- 必胜可能需要非常长的策略链。
- 也可能根本不存在红方必胜，而是黑方可守或黑方反胜。

因此下一阶段不应继续问“分数够不够大”，而应问：

```text
能不能找到一个小闭合证书？
能不能把某类局面压入残局库或可验证抽象？
能不能证明某个红方首着至少不坏于其他首着？
```

## 8. 建议的 MVP 路线

### MVP-1：历史正确的证书校验器

实现扩展状态：

```text
board + side + repetition_count_signature
```

并让证书校验器支持：

- 第三次重复造成者负。
- WIN 证书。
- LOSS 证书。
- DAG 子证书复用。

目标：先证明一些人工构造局面，而不是标准开局。

### MVP-2：DF-PN 搜索器

在校验器不变的前提下，把当前有界搜索换成 DF-PN：

- `pn/dn` 递推。
- GHI-safe 转置表。
- Pikafish 排序。
- 每次输出可验证证书，而不是只输出搜索结论。

目标：同样资源下，比当前 bounded search 多闭合一些小局面。

### MVP-3：阈值实验改写

把“评分阈值”改成可证命题：

```text
在固定样本 S 内，score >= T 的局面中，
有多少比例能被证书闭合为 WIN。
```

输出：

- `T`
- 样本覆盖率
- 证书闭合率
- 平均证明节点
- 最大证明节点
- 未闭合反例

这可以科学地逼近“分数和可证明胜之间的关系”，但不会把经验阈值误写成定理。

### MVP-4：残局库叶子

先做低子力局面：

```text
K + 少量攻子 + 双方防守子
```

用逆向分析得到 WDL 表，把它作为证明树叶子。

目标：让开局/中局搜索不必一直展开到将死，而是落到可验证表库。

## 9. 参考方向

- Zermelo / finite game determinacy：有限双人完全信息游戏可用反向归纳判定。
- Proof-number search：Victor Allis 的 PNS 路线，用 `pn/dn` 寻找最需要证明的节点。
- Proof-number search and transpositions：把树压成图，但必须处理循环与历史。
- GHI problem for DF-PN：重复规则依赖历史，缓存不能只看棋盘。
- Solving Checkers：真实大规模例子，启发式搜索、证明搜索和残局库一起工作。
- Fast memory-efficient retrograde algorithms：中文象棋残局库可做到很低内存占用。
- Proof Cost Network：网络预测证明成本，而不是普通胜率。
